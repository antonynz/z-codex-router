# Z Codex Router core

本文件是可移植的全局入口，不是自动加载的配置。每个新的独立任务先读取本文件，再解析 `z-codex-router/current.json` 指向的版本目录中的 `profiles/portable/default.toml`，然后读取一个最匹配的主 mode。只有确有跨领域必要时最多再读取一个辅助 mode；最终交付由主 mode 负责。后续轮次复用已确认的 tier、范围、验收条件与紧凑事实摘要；只有目标、影响面或验收标准实质变化时重新路由。

先确认真实目标、边界、风险和可验证的验收证据。只有缺少的信息会实质改变结果时才提问。优先复用现有实现、标准库、平台能力和已有依赖，最后才新增代码、文件、抽象或依赖。保护用户已有改动；不得臆造函数、接口、凭证、工具或审批权限。

## 统一判定轴（按顺序）

各 mode 只能提供领域化示例，不能改写本表或改变下列顺序。

1. 先判断是否有持久变更；没有持久变更且输入、路径、输出完整并可确定性完成时为 A0。
2. 再判断需求、根因和方案/关键取舍是否已确定：未确定时进入 C1；短提示且范围大、需要长期自主定位与设计时进入 C2；高风险或一次成功率优先时进入 C3。
3. 若三者已确定，按影响面与状态复杂度选择 A1（小、低影响、可逆局部变更）、B0（边界和验收明确的有界多步工作）、B1（明确目标的大型多文件工作）或 B2（多模块状态、异步/并发、性能、平台差异等复杂执行）。
4. 最后做风险复核；风险可以将任何路线提升到 C3。普通答复、说明或研究不因领域名称自动升级。

| Tier | 适用条件 |
| --- | --- |
| A0 | 输入、路径和输出完整的确定性只读查询、提取、格式化或无持久副作用的已知检查。 |
| A1 | 需求、根因和方案已确定；明确、小、低影响、可逆且有快速可靠检查的局部变更或产出。 |
| B0 | 需求、根因和方案已确定；边界与验收明确的有界多步工作、产出或实现。 |
| B1 | 需求、根因和方案已确定；影响面较大但状态简单的大型多文件实现。 |
| B2 | 需求、根因和方案已确定；多模块状态、异步/并发、性能、平台差异或其他复杂深入执行。 |
| C1 | 需求、根因或关键方案/取舍尚未确定，需要诊断、研究、架构或策略判断。 |
| C2 | 短提示、范围较大、需要自主定位和设计的长周期工程。 |
| C3 | 敏感数据、登录、支付、账户/权限、迁移/导出、生产影响、外部不可逆动作，或任务要求一次成功率优先。 |

## Profile 与运行时解析

分类不选择具体模型。解析 profile 时必须先验证 profile schema、启用状态、运行时元数据、平台/能力、以及 tier 到执行面的精确匹配。Profile 中列出的 mapping 只是该 profile 声明的参考或评估结果，不能替代实际运行时检查。任一字段缺失、不兼容、candidate 被禁用、能力交集为空或无法可靠解析时，记录 route exception 并停止；不得静默换模、猜测默认值或把更高 effort 视为兼容。

对 A1 及以上的持久变更，只有当前执行面与 resolved profile 所要求的精确组合、权限和工具能力同时匹配时才可直接执行。否则创建能力可用时应使用符合 profile 的独立执行面；创建能力不可用则报告 route exception。A0 与不产生持久副作用的只读分析可在 profile 不完整时完成，但不得以此隐含批准后续写入。

## 单代理实施与失败升级

默认单代理执行。单代理可在明确授权范围内修改源码、测试、脚本、项目配置和文档，并负责相称的 focused tests 与交付。不要为了形式上的角色所有权，把本可顺序完成的工作拆分成无收益的委派。

先区分失败类型。缺少需求、日志、权限、账号、SDK、设备、可复现环境或运行时元数据是阻塞，不靠更高 reasoning 或重试掩盖。每一级最多进行一次有证据的完整修正；只有 focused tests 仍失败、影响面扩大、出现冲突方案或高风险事实时才按 resolved profile 的升级策略重新判定。单次命令失败、无限重试或仅因环境缺失均不构成升级理由。

C1 先完成需求、根因或架构判断；方案固定后重新分类为具体实现 tier。全任务最多一次“实现 → C1 重新判断 → 实现”回环；第二次需要回到 C1 时停止并报告。C2 保持一个可审计的自主执行面，失败后按 profile 的止损规则停止或在风险确实提升时重判为 C3。C3 先保证风险判断、权限、回滚与验收边界；一次有证据的完整修正后仍失败时停止，而非无限重试。

## 角色、委派与权限

角色代表能力与权限边界，不按职业一一新增。仅在至少两个独立工作包、文件所有权不重叠、各自有独立验收且实际并行收益大于协调成本时才委派。共享 GUI、设备、模拟器和完整构建环境始终串行。单文件、单 focused test、根因未定或严格顺序依赖不委派。

| 角色 | 权限与边界 |
| --- | --- |
| code_writer | 仅写被分配的源码、测试、脚本和必要项目配置；可做格式、静态检查和 focused tests。 |
| docs_writer | 仅写被分配的工程文档、README 和变更说明。 |
| runtime_validator | 在实现稳定后执行 GUI、设备、模拟器、平台切换、完整构建与跨端验证。 |
| analyst | 只读证据、研究与方案分析。 |
| designer / media_creator | 只创建被分配的设计或媒体产物，不写业务实现。 |
| reviewer | 只读独立复核；只在明确高风险或高价值情形下使用。 |

委派前要说明执行拓扑、由 resolved profile 决定的执行面、任务范围、文件所有权、验收标准和失败升级依据。接收方仅获得完成其范围所需的目标、边界和验收信息，回报 `status`、`task_scope`、`changed_files`、`summary`、`key_evidence`、`checks`、`validation_result`、`remaining_risks` 与 `blockers`。

agent 不能替代审批人、法务、财务、业务签字人、账户管理员或对外承诺主体。对外发送、签署、支付、采购、账户/权限变更、公开发布和生产变更必须由具备权限的人明确确认并实际执行；草案、计划或自动化不能自动获得该授权。

## 验收、环境阻塞与质量记录

验收顺序为：行为正确 → 保护路径不变 → 回归测试通过 → 风险可接受 → 成本与时间。验证正向、失败和边界路径；实际未运行的命令、浏览器、设备、构建或平台不能表述为通过。缺少 SDK、签名、设备、测试数据、权限、目标平台或来源时，记录未验证项及影响。

每个主要任务保留紧凑质量记录：`predicted_tier`、`final_tier`、`reroute_reason`、`first_success`、`user_correction`、`route_exception`、`retry` 与 `coordination_cost`，以及输入/输出范围、执行拓扑、子任务数、耗时、测试结果、修改文件和保护路径状态。仅用真实、本地代表性证据调整 profile；不使用个人 IQ、个人样本、持久自动授权或未验证的通用榜单作为路由依据。
